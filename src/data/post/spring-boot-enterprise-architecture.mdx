读完后，你可以为“提交合同”列出事务边界、授权条件、并发冲突和通知失败的处理清单。本文保留目录图说明职责，没有提供可运行应用，不能据此认定权限、事务或审批机制已经实现。

## 从一个用例，而不是一张表出发

“提交合同”看似只是修改状态，实际可能涉及操作者权限、合同当前状态、必填信息、审批路径和操作记录。若直接围绕数据库表生成接口，这些规则很容易散落在控制器、页面和各种工具类中。先描述这个用例的输入、前置条件、成功结果与失败出口，比先决定模块数量更有帮助。

这里建议将接口层保持轻薄，由应用服务承接用例编排，把真正的业务规则放回领域对象或明确的规则组件中。基础设施则处理数据库、文件和外部接口。Spring Boot 并不要求固定代码布局，官方建议主应用类位于其他类之上的根包；下面的业务拆分是本文提出的示例，并非框架要求。[11]

## 以业务边界聚合代码

当系统只有少数业务时，可以先做清晰的模块化单体。在合同模块里组织接口、应用、领域与基础设施，比让全部模块共享一个巨大的服务目录更容易定位变化。模块间通过稳定的应用接口协作，避免其他业务直接操作合同模块内部的数据访问对象。

```text
contract/
  api/             # 请求与响应，身份上下文
  application/     # 提交、撤回、审批等用例
  domain/          # 状态与业务规则
  infrastructure/  # 数据访问、文件与外部系统
```

目录并不会自动形成边界。还需要约定依赖方向、哪些类型允许跨模块使用，以及公共能力如何演进。一个名为“公共”的模块如果收进所有业务对象，反而会让本来独立的需求重新耦合。

## 明确事务、并发和外部副作用

提交动作应在服务端重新检查合同状态与操作者权限，不能只依赖页面按钮是否禁用。并发操作也需要明确冲突策略，避免两个审批请求都以为自己处理的是同一份最新记录。可以根据数据访问方式选择适合的并发控制手段，而不是在所有地方随意增加锁。

使用 Spring 声明式事务时，应确认事务管理器、数据源和代理调用路径。默认代理模式只拦截经过代理的调用，同类内部自调用不会让被调用方法上的 `@Transactional` 新增事务拦截。未自定义回滚规则时，默认对 RuntimeException 和 Error 回滚，对受检异常不自动回滚；应按实际版本和配置显式确认业务异常策略，而不是捕获异常后返回“失败”就假定事务已回滚。[1]

事务也不是“自动防重复审批”的开关；默认隔离级别沿用底层事务系统设置。[1] 一种设计选择是按合同标识、当前状态和版本号做原子条件更新，检查实际更新结果，冲突时返回可理解的提示；也可以按数据库能力评估锁策略。请求重试还应单独约定幂等标识和唯一性约束，不能把并发控制等同于幂等。

数据库事务与外部消息、邮件或文件服务不是天然的整体。若提交成功后需要通知其他系统，应明确失败重试、重复处理和人工补偿方式。把外部调用放在事务代码附近，并不能证明它们会一起成功或一起回滚。方案评审时应把这些副作用单列出来讨论。

例如，可评估将待发送事件与业务变更写入同一本地事务，再由独立发送流程重试；这是设计建议，不是本文已实现的 outbox。发送可能重复，消费者仍需去重；单纯“提交后发一次通知”也不等于具备可恢复的可靠投递。

## 把权限和审计纳入用例

企业系统常见的权限不止“能不能打开页面”，还包括可访问的数据范围、可执行的业务动作以及可查看的敏感字段。应用服务应获取可信身份上下文，并在数据查询与状态变更处落实边界。页面隐藏菜单可以改善体验，但不能替代服务端权限判断。

建议让身份来自经过认证的服务端上下文，不信任请求体自报的用户、角色或部门；合同查询、附件下载、导出与变更动作都要检查对象范围。若选用 Spring Security 方法授权，需要显式启用相应配置；仅引入 Spring Boot Starter Security 不会默认启用方法级授权。[12] 方法注解也不能替代业务数据范围规则。

审计记录则应回答谁在什么时间，对哪个业务对象做了什么，以及结果如何。不要为了方便排查把完整证件、密钥或附件内容直接写入日志；需要追踪时优先使用业务标识和请求关联信息，并制定访问与保留规则。

## 让交接材料反映真实系统

最后为关键用例补充状态流转图、错误含义、配置项说明与恢复步骤。维护者应该能从“提交失败”找到责任模块和排查入口，而不是只拿到一张分层架构图。可维护的企业架构，不是层数更多，而是业务决定、技术机制和运维责任都有清楚的归属。

本文尚未实现控制器、认证与授权配置、数据库约束、事务管理、条件更新、幂等、通知发送或审计落库，也没有执行这些机制的验证。实施时应逐项定义成功、拒绝、冲突与补偿结果，不能把目录存在当成功能验收。
