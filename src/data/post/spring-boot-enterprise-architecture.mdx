## 从一个用例，而不是一张表出发

“提交合同”看似只是修改状态，实际可能涉及操作者权限、合同当前状态、必填信息、审批路径和操作记录。若直接围绕数据库表生成接口，这些规则很容易散落在控制器、页面和各种工具类中。先描述这个用例的输入、前置条件、成功结果与失败出口，比先决定模块数量更有帮助。

这里建议将接口层保持轻薄，由应用服务承接用例编排，把真正的业务规则放回领域对象或明确的规则组件中。基础设施则处理数据库、文件和外部接口。Spring Boot 项目的代码组织可参考[官方说明](https://docs.spring.io/spring-boot/reference/using/structuring-your-code.html)，下面的业务拆分是本文提出的示例，并非框架要求。

## 以业务边界聚合代码

当系统只有少数业务时，可以先做清晰的模块化单体。在合同模块里组织接口、应用、领域与基础设施，比让全部模块共享一个巨大的服务目录更容易定位变化。模块间通过稳定的应用接口协作，避免其他业务直接操作合同模块内部的数据访问对象。

```text
contract/
  api/             # 请求与响应，身份上下文
  application/     # 提交、撤回、审批等用例
  domain/          # 状态与业务规则
  infrastructure/  # 数据访问、文件与外部系统
```

目录并不会自动形成边界。还需要约定依赖方向、哪些类型允许跨模块使用，以及公共能力如何演进。一个名为“公共”的模块如果收进所有业务对象，反而会让本来独立的需求重新耦合。

## 明确事务、并发和外部副作用

提交动作应在服务端重新检查合同状态与操作者权限，不能只依赖页面按钮是否禁用。并发操作也需要明确冲突策略，避免两个审批请求都以为自己处理的是同一份最新记录。可以根据数据访问方式选择适合的并发控制手段，而不是在所有地方随意增加锁。

数据库事务与外部消息、邮件或文件服务不是天然的整体。若提交成功后需要通知其他系统，应明确失败重试、重复处理和人工补偿方式。把外部调用放在事务代码附近，并不能证明它们会一起成功或一起回滚。方案评审时应把这些副作用单列出来讨论。

## 把权限和审计纳入用例

企业系统常见的权限不止“能不能打开页面”，还包括可访问的数据范围、可执行的业务动作以及可查看的敏感字段。应用服务应获取可信身份上下文，并在数据查询与状态变更处落实边界。页面隐藏菜单可以改善体验，但不能替代服务端权限判断。

审计记录则应回答谁在什么时间，对哪个业务对象做了什么，以及结果如何。不要为了方便排查把完整证件、密钥或附件内容直接写入日志；需要追踪时优先使用业务标识和请求关联信息，并制定访问与保留规则。

## 让交接材料反映真实系统

最后为关键用例补充状态流转图、错误含义、配置项说明与恢复步骤。维护者应该能从“提交失败”找到责任模块和排查入口，而不是只拿到一张分层架构图。可维护的企业架构，不是层数更多，而是业务决定、技术机制和运维责任都有清楚的归属。
