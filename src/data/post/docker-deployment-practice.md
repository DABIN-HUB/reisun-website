读完后，你可以核对一份发布单是否覆盖镜像身份、变量来源、就绪条件和数据恢复。本文提供的是设计与交接建议，不是能直接执行的生产部署手册。

## 把发布定义成一个可识别的产物

“服务器上的容器已经启动”无法回答当前运行的是哪一份代码。建议为每次发布记录源码标识、镜像标识、构建时间、配置清单与变更说明。环境之间尽量推广同一份已经确认的镜像，而不是在不同机器上临时重复构建。Docker 的构建最佳实践介绍了基础镜像选择、多阶段构建和版本固定等方法，可按项目需要采用。[13]

镜像标签可以被重新指向，即使标签看起来像版本号，也不等于产物身份不可变；固定摘要可以固定对应镜像内容。[13] 建议记录实际拉取和运行的镜像摘要及目标平台，同时建立依赖更新与重新评估流程。固定产物身份是为了可追溯，不是为了永久停止安全更新。

## 将镜像、环境配置和业务数据分开

镜像承载应用与运行依赖，环境配置承载地址、开关与环境差异，业务数据应有独立的持久化与备份安排。下面只是 Compose 服务片段，仓库地址、发布标识与目录都是占位，尚不构成完整部署方案。使用前还需要定义访问入口、运行身份、目录权限与资源策略。

```yaml
services:
  app:
    image: registry.example.com/reisun/demo-app:${APP_RELEASE:?APP_RELEASE must be set}
    env_file:
      - ./app.env
    volumes:
      - ./data:/app/data
```

`APP_RELEASE` 必须来自 Compose 插值环境，例如调用它的 shell、项目 `.env` 或显式指定的 `--env-file`；`${VAR:?message}` 会在变量未设置或为空时终止解析。[6] 服务级 `env_file: ./app.env` 用于向容器传入环境变量，不应误认为它会为上述 `image` 提供插值变量。[14] 仓库和镜像均为虚构占位，片段没有提供实际版本、环境文件、应用或健康端点。

敏感值不应写进文章、代码仓库或镜像层。环境文件也不是自动安全的保险箱，应限制可读人员、明确传递方式，并优先采用运行环境已经提供的凭据管理能力。Compose secrets 可按服务授权并以文件提供给 Linux 容器，但需要应用主动读取；它不是自动加密宿主机源文件的保险箱，也不应假定所有 Windows 容器可照搬。[5] 日志输出同样需要脱敏，不能只保护启动配置。

## 给运行环境设定清楚的边界

只开放必要的访问入口，数据库和内部管理端点不要因为调试方便而直接暴露。运行身份尽量遵循最小权限，数据目录的归属与可写范围应预先安排。资源限制需要结合实际负载确认，不能把演示机器上的参数直接复制到生产。

还应规划日志轮转、磁盘容量与异常告警。日志可以帮助定位问题，也可能在无人关注时持续占用存储。对于需要持久化的数据，除了确认挂载位置，还要说明备份频率、恢复负责人和恢复步骤；“目录在容器外”并不等于已经具备可用备份。

## 区分启动、就绪和业务可用

进程存在只能说明程序还在运行。应用是否完成初始化、依赖是否可访问、关键业务能否完成，需要各自明确判断依据。监控页面不应因为容器状态正常，就把数据库故障或设备采集失败一起显示为正常。

Compose 默认按依赖顺序启动，但不会仅凭普通 `depends_on` 等待依赖业务就绪；需要定义 `healthcheck`，并对相应依赖配置 `condition: service_healthy`。[4] 这只覆盖约定的检查与启动门槛，不是持续可用保证；运行中断连仍需应用重试、超时与告警设计。健康检查应匹配实际应用能力，不能编造一个必然返回成功的检查代替就绪验证。

Docker Engine 重启策略针对容器退出或守护进程重启等情况，不等于健康状态变为 `unhealthy` 就自动重启，更不会修复坏配置或恢复业务数据。[7] 建议按故障类型约定重启、人工介入与观察窗口。上面的片段未配置健康检查、依赖就绪、重启策略或备份，不暗含这些保障。

发布后先核对产物身份，再按约定的入口检查配置加载、访问权限、日志和关键业务路径。若保留历史数据继续展示，应注明数据的成功时间与当前状态，避免旧结果掩盖本次读取失败。

## 回退不只是切换旧镜像

保留上一份可用产物和对应配置，并明确谁可以触发回退。涉及数据库结构、文件格式或外部接口变化时，要先评估旧程序是否仍兼容新数据。有些变更只能通过前向修复处理，不能承诺任何发布都可直接恢复到旧版。

建议在变更前定义可接受的数据损失范围、恢复时间与停写条件，并在隔离环境演练恢复。恢复备份可能丢失备份之后的新写入，外部已发送的通知或已完成交易也不会因切回镜像而撤销。需要同时评估数据、配置和外部副作用，不能直接用旧备份覆盖仍在写入的业务目录。

一份实用的交接清单，应同时说明发布产物、配置责任、数据位置、访问边界、观察入口与故障处理。容器技术可以统一运行形式，但可靠发布仍需要可执行的工程约定。
