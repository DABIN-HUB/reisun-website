## 先把“采到了”说清楚

一个采集程序能够读到数值，并不意味着这条数据已经可以用于生产判断。设备可能已经离线，屏幕却仍显示上次的温度；连接已经建立，点位映射却没有加载。设计的起点不是选择线程池，而是约定：谁产生数据、数据属于哪个点位、什么时候取得、当前质量如何，以及失败时保留什么证据。

建议先为一个设备建立点位清单，记录业务名称、协议地址、数据类型、单位、换算规则与采样要求。设备说明书中的地址和业务系统中的字段不是同一层概念。将这份映射作为可追溯的配置，而不是散落在协议驱动中的常量，后续变更才有边界。

## 给四类职责各留一个位置

协议适配器负责连接与读取，不直接决定订单或告警业务。调度器负责什么时候执行、哪些任务允许同时执行，不负责解释寄存器。解码层把原始响应转换为点位值，同时保留质量与来源。输出层再负责存储、上报或向其他应用提供数据。四者可以先存在于同一个 Java 应用中，不必一开始就拆成多个服务。

下面只展示数据边界，不是一份完整驱动实现。实际设计还需要处理原始类型、异常原因和时间来源，不能把所有设备值都无条件转成浮点数。

```java
public interface SampleSink {
    void accept(Sample sample);
}

public record Sample(
    String deviceId,
    String pointId,
    Object value,
    String quality,
    java.time.Instant collectedAt
) {}
```

## 把现场故障限制在局部

为每个设备规划连接、读取与重连的资源预算。一个响应缓慢的设备不应长期占住所有执行资源；重连也不应在网络恢复前无间隔地反复发起。可以使用有界任务队列，并明确满队列时选择跳过、延后还是告警。这里没有适用于全部设备的固定并发数，应以设备能力、链路条件与允许的数据延迟确定。

输出端也需要考虑积压。当存储暂时不可用时，应说明缓存容量、保留时间与丢弃策略。若业务要求断点补传，就需要额外定义持久化和重复数据识别，不能把“用了队列”当成数据不会丢失的保证。

## 让运行状态可以解释

状态展示至少区分配置有效、连接建立、采样成功和数据新鲜度。保留最后一次成功采样的时间，并把本次失败单独记录；旧值可以继续展示，但必须明确它已经过期。计数为零和没有取得计数也应区分，避免用绿色状态遮住未知情况。

交付前可以围绕设备断开、响应超时、点位配置错误、输出阻塞与进程重启整理检查清单。重点不只是系统能否恢复，还包括恢复前的旧数据如何标记、失败影响是否被隔离、操作人员能否找到下一步。采集架构的价值，是让每一次异常都落到一个明确的责任边界中。
